# 0003 — Assume retries: client-generated idempotency keys

- **Status**: Accepted, amended by 0023 (holds use a business key)
- **Date**: 2026-10-09 (date of the reference document; original decision date not recorded)
- **Related**: R4, R8, D-015, D-023

## Context

Replayed requests are a first-class risk: ambiguous timeouts, client retries and unstable
mobile networks mean the same request can reach the server several times. The client is not
under our control, so the server cannot rely on it to avoid duplicates. Queue entry (R4),
holds and payments (R8, D-015) must all produce a single effect per user intent.
No alternative was considered: ignoring retries would contradict the integrity goal (D-002).

## Decision

The server assumes retries will happen. Every non-idempotent operation accepts an idempotency
key generated by the client; a replayed request with the same key returns the original result.
This is the principle; the mechanism is chosen per operation (0023 uses the business key
(event, user) for holds).

## Consequences

- Retries are safe whatever the client does.
- Keys must be stored, with a retention period still to define (open question).
- The behaviour for a retry that arrives while the original request is still running is still
  to define (open question).
- With several seats per user, holds will need a technical key again (0023).

## Revisit when

Not recorded. Candidate signal: idempotency key storage shows up in write latency or storage
cost under load tests.
