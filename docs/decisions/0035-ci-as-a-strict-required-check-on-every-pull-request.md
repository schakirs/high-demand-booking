# 0035 — CI as a strict required check on every pull request

- **Status**: Accepted
- **Date**: 2026-11-01
- **Related**: D-018, D-019, D-022, D-026

## Context

Trunk-based development (D-018) needs `main` to stay always green: every short-lived branch
merges into it, and the next branch starts from whatever `main` holds. The repository is
public, so fork pull requests must be able to run CI with a read-only token and no secrets.
Work is solo, under a WIP limit of 2 (D-019). GitHub's merge queue requires the repository to
belong to an organization; this repository belongs to a user account, so a merge queue is not
available here. Much of the code is generated by Claude Code, so a
mechanical, unskippable gate matters more than it would with a single trusted human committer.

## Options considered

1. **Required status check alone** — the PR branch must pass CI before merging, but `main` can
   move after the PR's last run; a stale base can still merge an untested combination of the
   PR's changes and `main`'s newer commits.
2. **Required status check + "require branches to be up to date before merging" (chosen)** —
   the PR must be rebased onto the current `main` and re-run before it can merge, so the tested
   tree is always the merged tree, at the cost of a rebase-and-rerun on every PR when `main`
   moves.
3. **Merge queue** — would test the exact merge commit automatically, but requires the
   repository to belong to an organization; this repository belongs to a user account.

Separately, two mechanical choices:

4. **Pin actions by tag vs by commit SHA (SHA chosen)** — a tag (even `vN`) can be repointed by
   the action's maintainer or, if their account is compromised, by an attacker; the 2025
   `tj-actions/changed-files` compromise shipped malicious code under existing version tags.
   Pinning by the full 40-character commit SHA, with the tag kept only as a comment, removes
   that mutability; Dependabot (github-actions ecosystem) still offers version bumps as PRs to
   review.
5. **`paths`/`paths-ignore` filter on the triggers vs none (none chosen)** — a filter would skip
   CI on PRs that touch only excluded paths, but a required check that never runs blocks that PR
   forever (GitHub has no "skip if not applicable" for required checks); CI minutes are free on a
   public repository, so running the full `verify` on every PR has no real cost here.

## Decision

One workflow (`.github/workflows/ci.yml`, workflow name `CI`), one job (id and name `verify`),
running `./mvnw -B -ntp verify` from `backend/` on `pull_request` (targeting `main`) and `push`
to `main`. Least privilege: `contents: read` only, no secrets, `persist-credentials: false`.
Runner and JDK pinned for parity with local and, later, cloud environments (D-022): Temurin 25
on `ubuntu-24.04`. All actions are from `actions/*` and pinned by commit SHA. After the first
green run, the `main` ruleset requires the `verify` check and up-to-date branches; this is set in
the GitHub UI, not in a file.

## Consequences

- Every open PR must be rebased and its CI re-run whenever `main` moves; with WIP 2 this is a
  minor, bounded cost.
- Dependabot opens weekly bump PRs for the pinned action SHAs, each needing review before merge.
- Renaming the `verify` job id/name without updating the ruleset in the same change does not
  silently stop enforcement: the ruleset still requires a check named `verify`, no run ever
  reports under that name again, and GitHub treats a required check with no result as
  permanently pending — every pull request stays blocked from merging. A rename instead follows
  an expand/contract sequence: first land a workflow change that runs the job under both the old
  and the new name (or adds the new job alongside the old one), so the new name starts reporting
  while the old one still satisfies the ruleset; only once a pull request has gone green under
  the new name, switch the ruleset's required check to it and remove the old job.
- No required check exists until the ruleset is configured by hand after the first green run;
  until then `main` is not yet protected by this ADR's mechanism.

## Revisit when

The repository moves to a GitHub organization (merge queue becomes available), a second
deployable needs its own CI job, or the `verify` job's duration approaches about 10 minutes.
